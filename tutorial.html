0 · 先跑起来，再读代码

顺序很重要：先看到现象，再去看实现，否则很容易在各层之间迷路。

cd nanobot-ws-lab
python run.py                # 监听 127.0.0.1:9988
# 浏览器打开 http://127.0.0.1:9988/
# 右侧面板 = 协议示波器，逐条打印原始事件

敲一句「你好」回车，你会在右边看到这样一串事件——这串事件就是整个通道的"产品"：

{"event":"ready",     "chat_id":"47076dbc-...", "client_id":"..."}
{"event":"progress",  "text":"正在思考…",       "kind":"progress"}
{"event":"message",   "text":"调用工具 read_file(...)", "kind":"tool_hint"}
{"event":"delta",     "text":"我是迷你版 na",   "stream_id":"stream-47076dbc"}
{"event":"delta",     "text":"nobot。你刚",     "stream_id":"stream-47076dbc"}
...（若干 delta）
{"event":"stream_end","stream_id":"stream-47076dbc"}
{"event":"message",   "text":"我是迷你版 nanobot。...", "latency_ms":540}
核心认知：WebSocket 通道不产生内容，它只做三件事——把入站的字节翻译成消息、把事件路由到一个或多个连接、保证慢客户端不会拖垮别人。所有花哨功能都建立在这三件事之上。

1 · 全景与分层

真实实现有五千多行、四十多个文件，但结构极其规整。剥掉工程细节后只剩四层：

四层各管一件事，通道（②③）从不参与"内容生成"

为什么不把 Agent 塞进通道里？

因为通道的并发模型和 Agent 完全不同。通道要处理"几百条连接同时在线、随时断线重连"，Agent 要处理"一条会话串行执行、可能跑几十分钟"。两者用队列解耦后，各自可以独立限流、独立重启——这就是 bus.py 存在的全部理由。

为什么管理器只认识 BaseChannel，却叫得动 WebSocketChannel？

这是读这份代码时第一个会绊住人的地方：翻 ChannelManager 会发现它从头到尾没 import 过 WebSocketChannel，所有签名都是 BaseChannel。原因有两层：

一是多态。self.channels: dict[str, BaseChannel]（manager.py:136）里装的实际对象就是 WebSocketChannel 实例，由 manager.py:216 的 cls(section, self.bus, **kwargs) 造出来。所以 manager.py:380 那句 await channel.start() 按 MRO 查找，命中的是子类的 runtime.py:678，不是基类。

二是基类那份 start 根本不执行。base.py:74-84 的 start 带 @abstractmethod，函数体只有一个 pass——它是接口契约，不是默认实现。基类里只有 start / stop / send 三个抽象方法（base.py:74、86、91），其余十几个方法（_handle_message、send_delta、is_allowed…）都是带真实逻辑的共享实现。所以 BaseChannel 是"抽象契约 + 模板方法"的混合体，不是纯接口。

那具体类是怎么被找到的？靠字符串。websocket/manifest.py 只声明 runtime="nanobot.channels.websocket.runtime:WebSocketChannel"，真正 import 推迟到 ChannelPlugin.load_channel_class()（plugin.py:74，注释原文 "Resolve and validate the runtime class only when the channel is needed"）。这个函数还会显式拒绝 channel_cls is BaseChannel（plugin.py:86），也就是基类本身不允许被注册成通道。

为什么要绕这一圈？因为仓库里有 18 个通道，它们对管理器完全同构——只要能 start/stop/send 加 _handle_message 入总线就够了。若让管理器直接 import 具体类，启动时就会被拖着加载全部通道及其可选依赖（telegram / slack / discord 各家 SDK），任何一个没装就直接崩。字符串路径换来的是：依赖倒置 + 按需加载 + 缺依赖不致命。

唯一一处"具体类型感知"是 manager.py:183 的 if cls.name == "websocket"：因为 WebSocket 通道是唯一需要额外 gateway= 构造参数的通道。注意它比较的是 cls.name 字符串而非 isinstance，所以依赖方向仍然是倒置的。

对调试的直接后果：把断点打在 base.py:75 永远不会命中，要打在 runtime.py:678。

"插件注册"到底注册了什么？答案是：什么都没注册

先纠正一个容易带进来的直觉。如果你写过 Flask 的 app.register_blueprint()，或者接触过 pytest / WordPress 的插件体系，会默认"插件必须有一个注册动作"。nanobot 的通道完全没有这一步——没有中心注册表，没有 register() API。pyproject.toml:116 那行 [project.entry-points."nanobot.tools"] 只服务于工具，而且它是注释掉的占位示例。

那 manifest.py 是什么？它是声明，不是注册。整件事只有两步，第二步还不是插件做的：

① 你做的：建目录 + 摆一份清单         ② 框架做的：自己来翻
   nanobot/channels/<name>/              registry.py:20 _channel_package_names()
     ├── manifest.py   ← PLUGIN 变量        └─ pkgutil.iter_modules() 遍历子包
     ├── runtime.py                            └─ has_channel_package() 只判一件事：
     └── webui/index.ts                           manifest.py 这个文件在不在

判据就一行（plugin.py:127-131）：files("nanobot.channels").joinpath(name, "manifest.py").is_file()。目录里有没有 manifest.py，决定它是不是一个通道包——文件系统本身就是注册表。

方向是反的：拉，不是推。传统插件在导入时执行 register() 把自己交给框架（push）；nanobot 是 discover_plugins()（registry.py:30）主动去数目录（pull）。好处很实际：扫描阶段没有任何副作用——只 import manifest.py（plugin.py:135 注释原文："Load one package manifest without importing its runtime"），所以 telegram / slack / discord 这些可选 SDK 缺席时，扫描照样跑得通。

那"注册表"用什么顶替了？lru_cache 加一张运行期台账

没有全局字典，但有两处等价物。

一是缓存。plugin.py:134 给 load_channel_package 加了 @lru_cache(maxsize=None)。第一次扫到某个通道时走一遍 import + 校验，之后所有调用者（discover_plugins、load_channel_plugin、channel_default_enabled、load_channel_class 最终都汇到它）直接命中缓存。缓存键是通道名，行为上等价于一张只写一次的注册表。

二是运行期台账。实例化之后状态记在 ChannelManager 的四个字段（manager.py:136-139）：channels（runtime_name → 实例）、_channel_owners（runtime_name → 插件名）、_channel_runtime_specs（runtime_name → (插件名, instance_id)）、_channel_errors（构造失败原因）。它们都是扫描之后才产生的，不是提前登记来的。注意 channels 的键是 runtime_name 而不是插件名——websocket 没声明多实例，两者才恰好都等于 "websocket"。

谁都能摆一份 manifest.py，那凭什么信任它？四道静态校验

清单是数据，但校验是硬编码的。按顺序过四关，全程不导入通道运行时：

第 1 关 · 名字与形状合法（plugin.py:43-72）：ChannelPlugin.__post_init__ 用 [A-Za-z][A-Za-z0-9_]* 卡名字，强制 runtime / connector 必须是 module:attr 形态，webui 路径不许带 .. 逃出包外。

第 2 关 · 名实相符（plugin.py:145）：manifest.py 导出的 PLUGIN.name 必须等于目录名。在 websocket/ 里声明 name="telegram" 会直接抛 TypeError。

第 3 关 · 不许越界（plugin.py:157-172）：runtime 指向的模块必须以本包为前缀（startswith(f"{package_name}.")），再落到文件系统确认那个 .py（或 __init__.py）真实存在；webui/index.ts 同样要真实存在（plugin.py:173-178）。这条就是"自包含"的技术兑现——清单不能指向别的包。

第 4 关 · 类型正确（plugin.py:81-94，推迟到真正要用时才走）：必须 issubclass(BaseChannel)、必须不是 BaseChannel 本身、channel_cls.name 必须与 plugin.name 一致。

任何一关不过，discover_plugins 里的 try/except（registry.py:38-43）只打一条 logger.warning 就跳过这个通道，进程照常启动。单个通道写坏，不会拖垮 gateway。

对比工具侧：那里才是真插件机制，而通道故意不开放

同一个代码库里，nanobot/agent/tools/loader.py:68-87 的 _discover_plugins 走的是标准 importlib.metadata.entry_points(group="nanobot.tools")：第三方包 pip install 后只要在自己的 pyproject.toml 里声明条目就能被收集，校验也宽松得多（issubclass(Tool) 即可）。

通道侧没有这个分支。_channel_package_names()（registry.py:21-27）扫的是 nanobot/channels/ 这个固定物理目录，没有 entry_points 调用。想加新通道，你必须把目录放进 nanobot 自己的源码树——外部 pip 包装不进来。这是刻意的取舍：通道要处理凭证、权限、握手，收紧边界比开放生态更重要。

2 · 握手与 ready：第一条消息不是"hello"

WebSocket 的握手本质是一次 HTTP 请求升级。客户端发：

GET /?client_id=lab-abc HTTP/1.1
Host: 127.0.0.1:9988
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: bmFub2JvdC13cy1sYWIta2V5
Sec-WebSocket-Version: 13

服务端必须回一个"证明我看懂了你的 key"的值，算法是固定的哈希：

Sec-WebSocket-Accept = base64( sha1( Sec-WebSocket-Key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11" ) )

src/ws_proto.py · accept_key()

注意：这个 GUID 是 RFC 6455 写死的常量，不是可配置项。测试里我用官方示例做了断言校验：accept_key("dGhlIHNhbXBsZSBub25jZQ==") == "s3pPLMBiTxaQ9kYGzzhZRbK+xOo="。

握手成功后，服务端先说话

连接建立后服务端主动推第一条消息，而不是等客户端发：

{"event":"ready","chat_id":"47076dbc-...","client_id":"lab-abc"}

src/channel.py · _connection_loop() ／ nanobot runtime.py:794

这条 ready 里的 chat_id 就是这条连接的默认会话。客户端必须等它到了才能发消息——因为它得知道往哪个会话里发。

顺序陷阱：必须先 await connection.send_text(ready)，再把连接登记进订阅表。如果先登记后发送，一旦发送失败，订阅表里就留下一个"永远不会被唤醒"的僵尸连接，它占着内存却收不到任何东西。真实代码里有明确的注释说明这一点（runtime.py:823 "Register only after ready is successfully sent to avoid out-of-order sends"）。
TUI 的差异点：终端 UI 连的是同一个服务端，只是在 URL 上多带一个 ?terminal_protocol=1，服务端就会在 ready 里多回一段 terminal: {protocolVersion, gatewayId} 用于身份校验。除了这段额外字段，两边的后续流程完全一致。

3 · 入站信封：怎么识别"这是结构化请求"而不是"用户随便打的字"

连接上的每一帧文本都要先判断类型。策略很简单——能解析成带 type 字段的 JSON 就当信封，否则当裸文本消息：

def _parse_envelope(raw: str) -> dict | None:
    text = raw.strip()
    if not text.startswith("{"):          # 快速否决，避免无谓的 json 解析
        return None
    try:
        parsed = json.loads(text)
    except json.JSONDecodeError:
        return None
    if not isinstance(parsed, dict) or "type" not in parsed:
        return None                        # 有 JSON 但没 type，仍不算信封
    return parsed

4 · 订阅模型：为什么开三个标签页都能收到

通道里最核心的两个数据结构，就是两个方向相反的索引：

self._subs:        dict[chat_id, set[connection]]   # 谁在听这个会话？（扇出用）
self._conn_chats:  dict[connection, set[chat_id]]   # 这条连接听了哪些会话？（清理用）

src/channel.py · __init__() ／ nanobot runtime.py:377-380

一次 Agent 回复 → 三个连接同时收到；每个连接各自排队，互不影响

扇出代码只有四行，但有个关键细节：

connections = self.subscribers(msg.chat_id)   # 返回 tuple(...)，先拷贝！
for connection in connections:
    await self._safe_send_to(connection, raw, label=...)

src/channel.py · send() ／ nanobot runtime.py:1175 + outbound_projection.py:138

为什么必须拷贝？因为在遍历过程中，某个连接的发送失败会触发断线清理，而清理会 _detach——也就是修改正在被遍历的那个 set。Python 会直接抛 RuntimeError: Set changed size during iteration。真实实现用 tuple(self._subs.get(chat_id, ())) 就是为了这个。

5 · 出站投影：三件套 delta / stream_end / message

Agent 内部产生的事件种类很多，但线上字段是稳定契约。投影层负责翻译，认不出的事件直接丢弃：

内部事件线上 event关键字段客户端该怎么做
进度/思考messagekind: "progress"渲染成从属轨迹行，别当正式回复
工具调用messagekind: "tool_hint"同上，可折叠
流式 tokendeltatext, stream_id就地追加到同一个气泡
一段流结束stream_endstream_id, resuming去掉光标；resuming 表示后面还有
最终回复messagetext, turn_id, latency_ms以它为准落库，覆盖流式期间的累积
未知事件丢弃，不下发保证老客户端不被新事件打挂

src/projector.py · project() ／ nanobot webui/outbound_projection.py + outbound_wire.py

为什么不能只发 delta？因为 delta 是不可靠的增量流——网络抖动、浏览器后台挂起都可能丢帧，客户端累积出来的文本就是残缺的。所以协议用 stream_end 标记边界、用最后一条 message 给出权威全文。客户端策略是"流式期间渲染 delta 求快，收到 message 后以 message 为准求准"。

真实实现还多一层保险：stream_end 时会把服务端缓冲区里的全文一起带上（runtime.py:1330 send_delta() 里的 completed_text），客户端可据此校正。

6 · 背压：整个通道最值得学的一处设计

先看问题：Agent 正在流式输出，一秒推 200 个 delta。这时某个客户端网络卡住了（地铁进隧道、浏览器标签被挂起）。如果服务端只是 await connection.send(...)，会发生什么？

head-of-line blocking 的经典解法：把"可能阻塞的等待"从共享路径移进每连接私有队列

三道闸门，数字都来自真实实现（runtime.py:68-72）：

闸门迷你版nanobot 真实值超限后果
队列帧数上限max_frames=256_OUTBOUND_QUEUE_MAX_FRAMES = 256断开该连接（close code 1013）
未发字节上限max_bytes=8 MiB_OUTBOUND_QUEUE_MAX_BYTES = 8 * 1024 * 1024断开该连接
单帧发送超时send_timeout_s=10_OUTBOUND_SEND_TIMEOUT_S = 10.0断开该连接
 
async def _safe_send_to(self, connection, raw, *, label=""):
    state = self._connection_outbound.get(connection)
    if state is None or state.closing:
        return                                   # 已退役：静默丢弃

    utf8_bytes = len(raw.encode("utf-8"))         # 按字节算，不按字符算
    if state.queue.full() or state.buffered_bytes + utf8_bytes > self.config.max_bytes:
        self._retire(connection, state, reason="outbound queue full")   # 只踢这一个
        return

    try:
        state.queue.put_nowait(_Frame(raw, utf8_bytes, label))          # 永不阻塞
    except asyncio.QueueFull:
        self._retire(connection, state, reason="outbound queue full")
        return

    state.buffered_bytes += utf8_bytes
    self._start_writer(connection, state)
    await asyncio.sleep(0)    # 让空闲的写任务有机会立刻跑起来

src/channel.py · _safe_send_to() ／ nanobot runtime.py:1052

三个容易忽略的细节：
  1. 按字节而不是字符计数。中文一个字 3 字节，用 len(str) 会让内存预算变成三分之一。
  2. 写任务是"用完即走"的。队列空了就 return，不当常驻协程。发送时如果又有新帧入队，finally 里会补起一个新任务——这样避免了几千条空闲连接各养一个空转协程。
  3. 断开是异步的（retire），不是同步 close。投递路径绝不等待网络 I/O，只标记 closing=True 并丢一个任务出去。
动手验证：把 src/channel.py 里的 LocalConfig.max_frames 改成 2，重启服务，在浏览器连发几轮消息，终端就会打出 [backpressure] 断开慢客户端: 2 帧, 14 字节待发。这是最直观的一次背压演示。

7 · 连接生命周期：断开时到底要清理什么

WebSocket 是"随时可能断"的协议——网线拔了、笔记本合盖、进程被 kill，都不会有优雅的 close 帧。所以清理逻辑必须做到幂等且可多次调用：

async def _cleanup_connection(self, connection):
    state = self._connection_outbound.get(connection)
    if state is not None:
        state.closing = True
        writer = state.writer
        if writer is not None and writer is not current and not writer.done():
            writer.cancel()                          # 停掉写任务
            await asyncio.gather(writer, return_exceptions=True)
        while True:                                  # 清空队列，释放内存
            try: state.queue.get_nowait()
            except asyncio.QueueEmpty: break
        state.buffered_bytes = 0
        self._connection_outbound.pop(connection, None)

    for chat_id in tuple(self._conn_chats.get(connection, ())):
        self._detach(connection, chat_id)             # 双向索引都要摘
    self._conn_default.pop(connection, None)

src/channel.py · _cleanup_connection() ／ nanobot runtime.py:509

为什么必须先 tuple(...) 再遍历？因为 _detach 会修改 _conn_chats——也就是正在遍历的容器本身。这是本教程里第二次出现同一个陷阱，说明它在真实代码里是高频问题。

还有两个防泄漏设计值得注意：

  • 弱引用集合防僵尸：真实实现用 WeakSet[ServerConnection] 记录已退役连接（runtime.py:388），即使某处漏了清理，对象也会被 GC 回收，而不是永久留在字典里。
  • 退役后拒绝重新登记：_register_connection_outbound 会先检查 connection in self._retired_connections，防止一条已关闭的连接因为竞态又被加回订阅表。

9 · 六个坑（都在这份迷你实现里踩过或刻意保留）

坑 1 · 只 _subs.add() 却没建出站队列

订阅成功了，但消息一条都发不出去。我写第一版时就是这么错的：_safe_send_to 里 state = self._connection_outbound.get(connection) 拿到 None，直接 return 静默丢弃。

正解：_attach 里第一步就是 _ensure_outbound(connection)（真实实现对应 _register_connection_outbound）。这个 bug 是测试帮我抓出来的——test_fan_out_to_all_subscribers 断言失败，0 != 1。

坑 2 · 遍历 set 时修改它

扇出时某个连接发送失败 → 触发清理 → _detach 改 set → RuntimeError。正解：一律 tuple(...) 快照后遍历。

坑 3 · 先登记连接再发 ready

ready 发送失败就留下僵尸订阅。顺序必须是：发 ready → 登记订阅。

坑 4 · 用字符数当内存预算

中文一字符 3 字节，用 len(text) 会让 8 MiB 预算实际占用 24 MiB。正解：len(raw.encode("utf-8"))。

坑 5 · 把 kind: tool_hint 当正式回复渲染

客户端如果不区分 kind，"调用工具 read_file(...)"这种面包屑会和助手最终答案混在一起，对话看起来支离破碎。正解：从属轨迹行单独渲染。

坑 6 · 让写任务常驻空转

每条连接养一个 while True 的写协程，一万条空闲连接就是一万个协程。真实实现是"有帧才起、发完就退"，finally 里补跑兜底。

10 · 自测与动手练习

Q1 为什么服务端要主动发 ready，而不是等客户端先发一条 {"type":"hello"}？
看答案因为 chat_id 由服务端分配（uuid4），客户端在收到它之前无法构造合法的 message 信封。让服务端先说话，就把"分配会话标识"和"建立连接"合并成一次往返，客户端逻辑更简单。
Q2 三个浏览器标签都开着同一个 chat_id，其中一个崩溃了。其他两个会受影响吗？为什么？
看答案不受影响。①崩溃连接的清理只会 _detach 它自己；②每条连接有独立出站队列和独立写任务，一个连接的发送阻塞不会占用共享路径；③扇出用快照遍历，中途的集合变更不会破坏循环。
Q3 如果只发 delta、去掉 stream_end 和最终 message，会出什么问题？
看答案丢帧后客户端会永久显示残缺文本（没有权威全文可校正）；客户端也无法知道"这段说完了"，光标一直闪；服务端缓冲区不会被释放（真实实现里 stream_end 携带 completed_text 并清空 buffer）。
Q4 _safe_send_to 里那句 await asyncio.sleep(0) 有什么用？
看答案把控制权交还事件循环，让刚被 _start_writer 创建的写任务有机会立刻开始执行。没有它，如果调用方一直在同步循环里投递（比如一口气投几百个 delta），写任务可能饿死到本次投递全部结束才启动，造成延迟毛刺。
Q5 为什么超限时选择"断开连接"而不是"丢弃最老的帧"？
看答案因为聊天消息有语义完整性要求。丢掉中间几帧会让对话内容错乱，而客户端无法察觉。断开连接则是可恢复的显式失败：客户端重连后会走 hydrate 重放权威历史，用户看到的仍是完整对话。真实实现也是这个取舍。

一句话总结：WebSocket 通道的本质是一个带背压的事件路由器。
握手拿到身份 → 信封解析出意图 → 消息投给总线 → Agent 产出事件 → 投影成稳定字段 → 按 chat_id 扇出到每连接独立队列 → 超限就断开慢连接。
